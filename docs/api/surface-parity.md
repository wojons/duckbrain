# Surface parity: which capability lives on which surface

DuckBrain exposes one store through three surfaces that ship independently:
the CLI (`bin/duckbrain.ts`), the HTTP API (`src/cli/http.ts` plus
`src/http/routes/*`), and MCP (`src/mcp/server.ts`). They are written by hand,
so they drift — a verb can exist on one and silently be missing from the other
two. That had already happened: `tables declare` was CLI-only, `squash` had no
HTTP route, `s3` was reachable only from a shell, and keyword search had no MCP
tool. Each gap was found by reading code, never by a failing test.

This page is the fix for the *drift*, not for the gaps. `src/surface/capabilities.ts`
is the single source of truth: one row per capability, one cell per surface.
`src/surface/parity.test.ts` reads the real surfaces out of the code — the
Express mounts, the MCP registrations, the CLI command switch — and fails in
both directions:

- a route, tool or verb exists in the code and no row claims it;
- a row claims a surface and the code no longer has it.

`pending` means the capability is not implemented on that surface yet. `n/a`
means it never will be, with the reason attached. Adding a capability without a
row here turns the suite red.

Regenerate this section with `pnpm docs:surface` after editing the matrix; the
test also fails when the committed block is stale.
