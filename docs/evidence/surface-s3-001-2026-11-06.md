# SURFACE-S3-001 — the object store's own verbs, reachable from an agent

**Date:** 2026-11-06 · **Checkout:** `1c589ef5` (+ this proof) · **Script:**
`scripts/proofs/surface-s3-001.sh` (re-runnable; every failure is a FAIL line
and a nonzero exit) · **Bucket:** the local stub at
`scripts/proofs/surface-s3-001-stub.mjs` (ListObjectsV2 / PutObject /
GetObject / DeleteObject), never the production bucket.

The claim under test is not "a route exists". It is that an **agent holding
only an API key** can answer *"is this namespace pushed?"*, push it, run the
compaction runbook's ghost cleanup, and (as an admin) destroy a namespace's
remote objects — through the same engine, lock and deadline the CLI uses — and
that the destructive verbs are gated. An in-process route test cannot show
that (it never boots the binary), so the proof drives `node bin/duckbrain.js
http` on scratch ports 28780-28782 with a scratch config and namespaces root
under `~/.hermes/cache/scratch/`. Port 3000 and the production data directory
are never touched.

## What each half rules out

- **The counts are not fabricated.** `uploaded=8` is what `syncNamespace()`
  returned after walking the real namespace and PUTting to the stub; the
  follow-up status lists the bucket and finds 8 data objects plus the engine's
  own 1-object checksum ledger. The second sync uploading 0 is the engine's
  delta logic, not a hard-coded zero.
- **"Drift" is not `local - remote`.** The ledger object would make every
  healthy namespace look one object ahead forever, so the route reports
  `objects.remote` (raw listing), `objects.bookkeeping` (the engine's own
  state) and `objects.data` (the difference), and `drift.objects` compares
  local against **data**. An absent listing (probe off, or the bucket did not
  answer) is `null`/"unknown", never `0`.
- **The lock objection is answered, not ignored.** SURFACE-HTTP-OPS-001 kept
  `s3 sync` CLI-only because a disconnected caller could leave the lock held.
  The route runs the same `acquireLock` and answers a second trigger with
  `409 SYNC_IN_PROGRESS` (pinned in `src/http/routes/s3.test.ts`), and every run
  stays bounded by the engine's deadline watchdog. Progress streaming and
  mid-flight cancellation are still CLI-only — stated, not pretended.
- **Ghost cleanup is scoped.** The CLI `s3 ghosts --sweep` sweeps the whole
  root; the route mounted under one namespace prunes only that namespace
  (`only:` option threaded into `sweepGhostSyncState`). The proof shows
  `dead-x` pruned while `dead-y` survives.
- **Destruction is gated and audited.** Dry run by default, then `dryRun:false`
  + `confirm:true` + a `reason`; the plan is re-listed at execution. One
  lifecycle ledger line per run (`surface: "rest"`, `principal`, counts).
- **The control is the falsifier.** Against the pre-change commit the same
  request is `404 ROUTE_NOT_FOUND`, so the PASS lines above are attributable to
  this change.

## Decision change

`docs/api/ops-surface-decisions.md` moves `s3 sync`, `s3 clear` and `s3 ghosts`
from "CLI-only" to "Exposed" with the lock contract written down; `s3 query`
(arbitrary SQL with host credentials) and `s3 config` (host diagnostic, values
already in the status response) remain CLI-only with their reasons. No MCP tool
ships for these verbs: every one is reachable over HTTP with an API key, which
is what the compaction runbook needs end to end, and a third surface is a third
thing to keep in sync.
